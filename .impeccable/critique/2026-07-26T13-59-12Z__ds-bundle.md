### A real bug found and fixed mid-verification

The first regeneration of `ds-bundle/` shipped with a **stale compiled CSS** — the JS had all the fixes, but `_ds_bundle.css` was missing `focus-visible`, the `-700` tokens, and the `sm:` responsive breakpoint entirely, which caused a **new regression**: DataTable rendered both its mobile-card and desktop-table layouts simultaneously, and none of the P0/P1 fixes were visually real despite being correct in source. This was diagnosed (the `_ds_bundle.css` in `frontend/packages/ui/nicarunner-ds.css` was never rebuilt after the `-700` tokens were added — it's a hand/CLI-regenerated artifact, not something `npm run build` produces) and fixed by rebuilding it properly with the Tailwind v4 CLI. Re-verified via `.render-check.json` (`thin`/`collapsed`/`variantsIdentical` all false) and by reading the actual screenshots.

### A finding that looked like a bug but wasn't

Assessment A initially flagged Modal/DataTable/Label as rendering without background/border/text color because they reference CSS custom properties (`--bg-card`, `--text-hi`, `--radius-card`, etc.) that don't exist in `_ds_bundle.css`. Verified: these are **real, intentional app-level theme tokens**, already defined per-theme (dark/light/brand) in `frontend/src/index.css` — components are designed to inherit them from whatever `data-theme="..."` wrapper the consuming app applies. The standalone `ds-bundle/.review.html` preview harness never sets `data-theme` on anything, so these components correctly show their "no theme applied" state there — this does not reproduce in the real NicaRunner frontend app, which does apply a theme. Confirmed no `data-theme` attribute exists anywhere in the preview harness.

That said, this does surface one legitimate, smaller gap: **the components have no CSS fallback values for these tokens** (e.g. `var(--bg-card)` instead of `var(--bg-card, white)`), so a real consumer who forgets to wrap in a themed ancestor would see the same unstyled Modal/DataTable/Label in production. Worth a follow-up, not a blocker.

## Priority Issues (remaining)

**[P2] MetricCard's `orange` and `amber` (dispute) variants are technically distinct but perceptually too close.** Both render as similar warm orange-brown in the actual screenshot. For a status system meant for at-a-glance scanning, this defeats the "recognition over recall" goal and is a mild concern for colorblind users. Fix: push `dispute`/amber toward a more saturated gold/amber, or add a non-color differentiator.

**[P2] No CSS fallback values for app-level theme tokens consumed by Modal/DataTable/Label.** A consumer that doesn't apply a `data-theme` wrapper (or a future theme that's missing one of these variables) gets a fully unstyled component with no visual boundary. Fix: add fallback values to every `var()` call in these three components (`var(--bg-card, #fff)`, `var(--radius-card, 0.5rem)`, etc.).

**[P3] Focus-visible ring correctness at runtime is unverified.** The CSS rule and the JS class application both check out at the source level, but static screenshots can't show a `:focus-visible` state, so actual paint (z-index, clipping, offset) needs a live/interactive check before full confidence — not a regression, just an open verification gap.

**[P3] `.prompt.md` documentation remains unchanged** — still bare `.d.ts` restatements with no usage guidance. Lowest-priority remaining item from the original critique.
