# Development database

Local development runs against **Postgres 16**, the same engine as production on Render.

## Start

```bash
docker compose up -d
dotnet ef database update --project src/NicaRunner.Infrastructure --startup-project src/NicaRunner.Api
dotnet run --project src/NicaRunner.Api
```

Migrations are **not** applied automatically at startup in development. `Program.cs` only
runs the auto-migrate-on-boot call when `!app.Environment.IsDevelopment()` — production
(Render) has no easy pre-deploy shell, so it migrates on boot; local development is
expected to run `dotnet ef database update` manually first. Skipping this step fails with
errors like `relation "Users" does not exist`.

## Reset to an empty database

```bash
docker compose down -v
docker compose up -d
dotnet ef database update --project src/NicaRunner.Infrastructure --startup-project src/NicaRunner.Api
```

## Generate a migration

```bash
dotnet ef migrations add <Name> \
  --project src/NicaRunner.Infrastructure \
  --startup-project src/NicaRunner.Api
```

With `Database:Provider=Postgres` in `appsettings.Development.json`, this now emits Npgsql
DDL by default. Before opening a PR, read the generated file and confirm:

- text columns are `text` or `character varying(n)`, **not** `TEXT`
- timestamp columns use a real Postgres timestamp type consistent with the existing
  migrations (this codebase's `FixPostgresDateTimeColumns` produces
  `timestamp without time zone`), **not** `TEXT`
- integer keys are `integer` with `GENERATED BY DEFAULT AS IDENTITY`, **not** bare `INTEGER`

## Why the provider is configuration, not environment

It used to be `builder.Environment.IsDevelopment()`. Because every developer machine is
`Development`, `dotnet ef migrations add` always ran with Sqlite active and emitted Sqlite
DDL — which Npgsql then ignored in silence. Four migrations exist only to repair that
damage: `FixPostgresIdentityColumns`, `FixPostgresBooleanColumns`,
`FixPostgresDateTimeColumns`, `FixPostgresDecimalColumns`.

## Sqlite is still used, on purpose

Five test classes build a context over Sqlite in memory and create the schema with
`Database.Migrate()` or `EnsureCreated()`. They run in milliseconds and give real
migration coverage. They stay on Sqlite; moving them to Testcontainers would trade a
millisecond suite for a multi-second one with a Docker dependency in CI.

The consequence is that **the migration set must keep applying under both providers**.
Where the two genuinely diverge, guard the SQL:

```csharp
if (migrationBuilder.ActiveProvider != "Npgsql.EntityFrameworkCore.PostgreSQL")
    return;
```

To run the API itself on Sqlite, set `Database:Provider` to `Sqlite` in
`appsettings.Development.json`.

## Known debt

EF Core does not officially support one migration assembly serving two providers; the
supported approach is a separate migrations assembly per provider. The `ActiveProvider`
guards are a workaround. Restructuring 22 migrations against a live production database
is its own project and has not been done.
